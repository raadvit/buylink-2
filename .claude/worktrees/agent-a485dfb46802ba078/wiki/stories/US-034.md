## Why / Business Goal
Aktuálně když se validace selhá, přichází uživatel o své zadání. Story se neodsílá bez uložení, takže padne-li kontrola, nemá se co aktualizovat. Business motivace: **zabránit ztrátě dat a zvýšit důvěru v systém** — user story je trvalá, ať validation uspěje či ne.

## Co se zobrazuje
Stejné UI jako dnes — tlačítko 'Odeslat týmu k validaci'. Žádné nové prvky, dialogy, progress indikátory ani notifikace.

## Jak se to chová
Změna logiky procesu: (1) Klik na 'Odeslat' → uloží aktuální story (vytvoří GitHub issue v `draft` stavu + wiki soubor); (2) poté spustí validační pipeline (Conflict Detector → Architect); (3) story zůstává editovatelná během běhu validace; (4) padne-li validace, uživatel vidí error zprávu ale story je zachovaná; (5) projde-li validace úspěšně, story se přesune do `ready-for-arch`. Proces lifecycle zůstává stejný, jen změňme pořadí operací (Save → Validate místo Validate bez uložení).

## Acceptance Criteria

### Funkční podmínky
- [ ] Kliknutí na 'Odeslat týmu k validaci' nejdříve uloží story do GitHub issue se statusem 'conflict-check'
- [ ] API response jasně vrátí `success: true/false` — frontend bude vědět, zda se uložení povedlo
- [ ] Pokud uložení selhalo, formulář zůstane v edit módu (tlačítka enabled, status: error)
- [ ] Pokud uložení uspělo, validace se spustí asynchronně (session v backend je vytvořena)
- [ ] Timeline se zobrazí s aktuálním `draft` statusem po úspěšném uložení
- [ ] Pokud validace spadne, story zůstane uložena v GitHub issue (permanentní data)
- [ ] Pouze admin má právo odeslat story — non-admin obdrží error 'Permission denied'
- [ ] Story se neuloží dvakrát — pokud user spustí `/api/submit` dvakrát, druhý pokus přepíše první (create-or-update pattern)
- [ ] GitHub issue body obsahuje `- Status: conflict-check` ihned po uložení
- [ ] Wiki soubor se vytvoří/aktualizuje v přesné chvíli, kdy se vytvoří/aktualizuje GitHub issue (atomicita)

### Nefunkční podmínky
- [ ] Zápis do GitHub musí být atomický — buď se vytvoří/aktualizují oba (issue + wiki), nebo nic (rollback)
- [ ] Pokud wiki zápis selže, GitHub issue se neuloží (rollback obojího, vrátit chybu)
- [ ] Session/validace smí začít pouze pokud je zápis potvrzen v databázi (async, ale ne dřív)
- [ ] Timeout pro uložení: max 5 sekund (user feedback — 'saving…' status bar)
- [ ] Timeout pro validační session: max 60 sekund (pokud déle, vrátit async status — 'Story je uložena, validace běží na pozadí')
- [ ] Frontend musí rozlišit: success (story je uložena, agenti pracují) vs. error (story se neuložila, zkus znovu)
- [ ] Pokud session spadne, user story zůstane v GitHub se statusem z poslední úspěšné fáze (rollback jen validace, ne storage)

## Test Cases
- [ ] Happy path: Admin vyplní formulář → klikne 'Odeslat' → `/api/submit` vytvoří GitHub issue se statusem 'conflict-check' → validace běží (Product Owner, Conflict Detector, Architekt) → status se změní na 'validated'
- [ ] Failure during save: GitHub API je down → `/api/submit` vrátí `{success: false, error: 'GitHub API unreachable'}` → formulář zůstane enabled → user vidí error notification → může zkusit znovu
- [ ] Failure during validation: Story se uloží OK → Conflict Detector detekuje konflikt → issue se aktualizuje s error comment → timeline ukazuje red errorStep flag
- [ ] Permission denied: Non-admin user se pokusí odeslat → `/api/submit` vrátí `{success: false, error: 'Only admin can submit'}` → formulář zůstane enabled
- [ ] Double submit protection: User klikne 'Odeslat' 2x za sebou → pouze jeden HTTP request se provede (frontend disables buttons) → GitHub issue existuje → druhý pokus se aktualizuje (create-or-update)
- [ ] Draft update + submit: User uloží draft → změní data → klikne 'Odeslat' → `/api/submit` dostane `issue_number` a `wiki_path` → aktualizuje issue + wiki → spustí validaci
- [ ] Partial validation failure: Architekt Phase 1 timeout → session se zastaví → issue zůstane se statusem z poslední fáze (conflict-check nebo ready-for-arch) → user obdrží warning notification
- [ ] Wiki save rollback: GitHub issue se vytvoří OK, wiki zápis selže → GitHub issue se smaže (rollback) → `/api/submit` vrátí `{success: false, error: 'Wiki sync failed'}` → user zkusí znovu

## Technické doporučení

### Problém
Aktuální workflow ztratí data formuláře pokud se během validace vyskytne chyba. Cíl: uložit story do GitHub issue PŘED spuštěním validačních agentů.

### Řešení: Split workflow na dvě fáze

#### Backend (`story_builder.py`)

**Fáze 1: Save (v `submitForm()` frontend → `/api/submit` POST)**
- Pokud `issue_number` a `wiki_path` nejsou v payloadu: 
  - Vytvoří nový GitHub issue se statusem `conflict-check` v body
  - Vytvoří wiki soubor `wiki/stories/US-NNN.md` (draft verze)
  - Vrátí `{success: true, session_id: '...', issue_number: N, wiki_path: 'wiki/...'}`
- Pokud `issue_number` a `wiki_path` jsou v payloadu (update draft):
  - Aktualizuje GitHub issue body
  - Aktualizuje wiki soubor
  - Vrátí stejný response
- **Pokud uložení selže** (GitHub API error, network, atd.):
  - Vrátí `{success: false, error: 'msg'}` — **validace se nespustí**
  - Frontend se vrátí do edit módu

**Fáze 2: Validate (asynchronní, spuštěna v backend session až po OK Phase 1)**
- `store.update_session()` nastaví `validation_phase: 'product_owner'`
- Product Owner → Conflict Detector → Architekt běží jako dnes
- Po skončení se GitHub issue aktualizuje s finalním statusem (`validated` nebo `conflict-check` s errorStep flagem)

#### Frontend (`app.js`)

`submitForm()` se změní minimálně:
- Pokud `_draftIssueNumber` a `_draftWikiPath` nejsou nastaveny (nový submit):
  - Frontend NEJDRÍVE zavolá `/api/save` (stejný call jako "Uložit na později")
  - Pokud OK: dostane `issue_number` a `wiki_path`, uloží si je
  - Pak zavolá `/api/submit` s `issue_number` + `wiki_path` v payloadu
- Pokud `_draftIssueNumber` a `_draftWikiPath` JIŽ existují (update draft + submit):
  - Frontend zavolá `/api/update` (update draft)
  - Pokud OK: zavolá `/api/submit`

**Alternativa (minimální změna):** Backend automaticky uloží draft pokud v payloadu `/api/submit` chybí `issue_number` a `wiki_path`, teprve pak spustí validaci.

#### Dotčené soubory
- `task-forge/story_builder.py`: Split `run_team_validation()` → `save_story_to_github()` + `run_team_validation()`
- `github_helper.py`: Create-or-update pattern pro GitHub issue (pokud existuje issue_number, updatuj; jinak vytvoř nový)
- `task-forge/static/app.js`: `submitForm()` se změní aby volala `/api/save` + `/api/submit` sekvenciálně, nebo backend to udělá atomicky
- API endpoint `/api/submit`: musí nejdřív uložit (sync), pak spustit validaci (async)
- Session state: přidá se field `issue_saved_at` či `saved_issue_number` aby se vědělo, že draft je v GitHub

#### API kontrakt

**POST `/api/submit`**
Input:
```json
{
  "name": "...",
  "epic": "EP-01",
  "role": ["admin"],
  "what": "...",
  "how": "...",
  "flags": [...],
  "issue_number": (optional) 123,
  "wiki_path": (optional) "wiki/stories/US-001.md"
}
```

Output (success):
```json
{
  "success": true,
  "session_id": "uuid",
  "issue_number": 123,
  "issue_url": "https://github.com/...",
  "wiki_path": "wiki/stories/US-001.md"
}
```

Output (failure):
```json
{
  "success": false,
  "error": "GitHub API is down" 
}
```

#### Chování v timeline
- Po úspěšném `/api/submit` se timeline přepne na `draft` (právě uloženo)
- Pak agenti pracují → timeline se změní podle `validation_phase` (conflict-check, arch, done)
- Pokud `/api/submit` spadne: timeline se neaktualizuje, formulář zůstane enabled

#### Role kontrola
- Only admin může odeslat story — kontrola na backendu v `/api/submit`
- Pokud user není admin: vrátí `{success: false, error: "Permission denied"}` — frontend to zobrazí

### Výhody
- Story se nikdy neztratí (uloženo v GitHub)
- User vidí GitHub issue URL hned po uložení
- Pokud agent spadne, data zůstávají v GitHub
- Failsafe: pokud zápis do GitHub selže, validace se nespustí
